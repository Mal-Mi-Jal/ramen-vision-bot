## 전체 그림

```
사진 ─▶ ① 보기 (VLM)          ─▶ ② 검색 (RAG)              ─▶ ③ 판단 (LLM)         ─▶ ④ 답변
        국물·색·토핑만 추출        국물 유무=필터 + 벡터 검색       후보 중에서만 선택          문서 섹션 조립 + 출처
        vision.py                knowledge.py / judge.py       judge.py                answer.py
                                                                          └─ FastAPI 데모 (api.py + web/)
```

한 줄 요약: **작은 모델에게는 쉬운 일(보기)만 시키고, 어려운 일(판단)은 출처가 있는 문서에 맡긴다.**

## 기술별 정리

### 1. 로컬 LLM 실행: Ollama + 양자화
- **Ollama**: 내 PC에서 LLM을 돌려 주는 서버 (`localhost:11434`). 파이썬은 HTTP로 요청을 보낸다.
- **양자화(4bit)**: 모델 숫자의 정밀도를 낮춰 크기를 줄이는 기술. 7B 모델이 약 15GB → **6GB**로 줄어 8GB GPU에 들어간다.
- **제약**: 8GB에는 7B 모델이 하나만 올라간다 → 판단 단계도 **같은 VLM을 텍스트 모드로 재사용**.
- 코드: `ramen_bot/vision.py`

### 2. VLM(Vision-Language Model)과 이미지 토큰
- **VLM**: 이미지와 글을 함께 입력받는 LLM (`qwen2.5vl:7b`).
- **이미지도 토큰을 먹는다**: 약 28×28픽셀마다 토큰 1개. 4000×3000 폰 사진은 컨텍스트 한도(4096)를 넘었다.
- **해결**: 긴 변 1024px로 축소(약 1000토큰) + `num_ctx=8192` + EXIF 회전 보정.
- 포인트: 해상도와 토큰 비용의 **트레이드오프**를 직접 겪고 조정했다.

### 3. 작업 분해: "보기"와 "판단"의 분리 ⭐ 핵심
- **문제**: VLM에게 "무슨 라멘이야?"라고 물으면 지식이 부족해 지어냈다 (17%).
- **해결**: VLM에게는 **눈으로 확인 가능한 것만** 묻고(국물 유무, 투명도, 색), 판단은 지식 문서에 맡겼다.
- **세부 기법**
  - 질문은 **영어로**: 작은 모델은 영어가 가장 강하다.
  - **선택형(enum)**: 자유 서술을 없애 지어낼 여지를 줄였다.
  - 토핑은 **예/아니오 체크리스트**: "나열해"라고 하니 파인애플·파스타를 지어냈다.
- **결과**: 같은 모델로 국물 없는 라멘 인식 1/3 → 3/3, 반복 루프 0건.

### 4. Structured Output (출력 형식 강제)
- JSON 스키마를 주면 모델이 반드시 그 형식으로 답한다 (`format=SCHEMA`).
- **`enum`**: 정해진 값 중에서만 고르게 해서 코드로 자동 채점할 수 있다.
- **안전장치 세트**
  - `temperature: 0` — 매번 같은 답 (재현성)
  - `num_predict` — 출력 길이 상한. 반복 루프에 빠져도 끝난다
  - `maxItems` — 배열 길이 제한
  - JSON 파싱 실패 → `invalid`로 기록하고 계속 진행

### 5. 임베딩 + 벡터 DB
- **임베딩(`bge-m3`)**: 문장을 숫자 벡터로 바꿔, **의미가 비슷하면 벡터도 가깝게** 만든다. 한국어·일본어·영어 지원.
- **코사인 유사도**: 두 벡터의 방향이 얼마나 비슷한지로 가까움을 잰다.
- **Chroma**: 벡터를 저장하고 가까운 것을 찾아 주는 DB. 메타데이터(종류, 섹션, 출처)도 함께 저장한다.
- **청킹(chunking)**: 문서를 `## 제목` 섹션 단위로 자르고, 청크 앞에 문서 제목을 붙여 짧은 섹션도 어느 라멘 얘기인지 알 수 있게 했다.
- 코드: `ramen_bot/knowledge.py`, 문서: `knowledge/*.md`

### 6. 하이브리드 검색과 RAG의 함정 ⭐ 면접 단골

| 발견한 문제 | 원인 | 해결 |
|---|---|---|
| "국물 없음" 검색에 국물 라멘 문서가 나옴 | **임베딩은 부정 표현에 약함** | 확실한 정보는 **메타데이터 필터**로 (하이브리드 검색) |
| 모든 검색에서 "국물" 섹션만 상위 | 모든 문서에 같은 섹션이 있음 | 검색 대상을 "사진으로 구분하는 법" 섹션으로 좁힘 |
| 토리파이탄 문서가 모든 검색에 걸림 | 비교 문장이 많아 **허브 문서**가 됨 | 비교 문장을 별도 섹션으로 분리 |

- 결과: 검색 재현율 61% → 91%
- 포인트: RAG는 벡터 DB에 넣기만 하면 되는 게 아니라 **문서 구조와 검색 전략**이 성능을 좌우한다.

### 7. 판단 단계 설계 (LLM을 믿지 않는 설계)
- **후보 제한**: 검색된 종류 중에서만 고르도록 enum으로 제한.
- **근거 먼저, 결론 나중**: LLM은 앞에서부터 생성하므로 결론을 먼저 쓰면 근거를 짜맞춘다. 단, 작은 모델에게 한국어 근거를 길게 쓰게 하면 망가져서(4%) **짧은 영어 근거**로 해결.
- **출처는 코드가 붙인다**: LLM은 URL도 지어낼 수 있다.
- **후보가 하나면 LLM 호출 생략**: 국물 없음 → 바로 아부라소바. 더 빠르고 정확하다.
- 코드: `ramen_bot/judge.py`

### 8. 답변 생성: 생성하지 않고 조립하기
- 한국어 설명을 LLM에게 쓰게 하지 않고 **지식 문서 섹션을 꺼내 조립**했다 → 모든 문장에 출처가 있고 할루시네이션 여지가 없다.
- 포인트: LLM은 **판단에만** 쓰고, 생성은 검증된 문서로 대체했다.
- 코드: `ramen_bot/answer.py`

### 9. 평가 방법론 ⭐ 가장 큰 차별점
- **Baseline(기준선)**: 개선 전 수치(VLM 단독)가 있어야 개선 폭을 말할 수 있다.
- **정답률과 검색 재현율을 분리 측정**: 틀렸을 때 검색 문제인지 판단 문제인지 구분한다.
- **단계별 실험(ablation)**: v1 → v2 → v3로 한 번에 하나씩 바꿔 각 변경의 효과를 확인.
- **과적합 인정 + held-out 검증**: 튜닝용 사진 76%, 새 사진 60%. 정직한 숫자를 보고.
- **데이터 누수 방지**: 테스트 사진을 보고 쓴 메모("프로젝트 관찰")는 검색에서 제외.
- **테스트 세트 오염 방지**: 새 사진에서 찾은 약점은 기록만 하고 고치지 않았다.

### 10. FastAPI 웹 데모
- **`def` vs `async def`**: 오래 걸리는 동기 코드는 `def`로 둬야 FastAPI가 별도 스레드에서 실행해 서버가 멈추지 않는다.
- 파일 업로드(`UploadFile`), 임시 파일 처리(Windows 대응), 크기·형식 검증.
- **XSS 방지**: 문서 텍스트를 화면에 넣기 전에 HTML 이스케이프.
- 코드: `ramen_bot/api.py`, `web/index.html`

### 11. 데이터·개인정보·라이선스
- **EXIF GPS**: 폰 사진에 위치정보가 숨어 있다 → 원본 사진은 `.gitignore`로 제외.
- **CC 라이선스**: 위키미디어 사진은 올리지 않고 저작자·라이선스 목록만 공개 (`data/test_sources.csv`).
- **git 기록 정리**: 첫 push 전에 과거 커밋의 이메일을 GitHub 비공개 이메일로 교체 (백업 → 재작성 → 검증 순서).

### 문법 대응표 (이 프로젝트에 실제로 나오는 것만)

| Python | Java로 치면 | 예시 위치 |
|---|---|---|
| `def f(path: Path) -> dict:` | `Map<String,Object> f(Path path)` — 타입 표기는 **힌트일 뿐**, 컴파일러가 강제하지 않음 | 모든 파일 |
| `dict` `{"soup": "yes"}` | `Map<String, Object>` | `vision.py` |
| `list` `["shio", "shoyu"]` | `List<String>` | `vision.py` FEATURES |
| `f"{name}: {value}"` | `String.format("%s: %s", name, value)` | print 문 |
| `with open(...) as f:` | `try (var f = ...) { }` (try-with-resources) | `api.py` 임시 파일 |
| `try: ... except X: ...` | `try { } catch (X e) { }` | `vision.py` JSON 파싱 |
| `[c["style"] for c in chunks]` | `chunks.stream().map(c -> c.get("style")).toList()` | `judge.py` (리스트 컴프리헨션) |
| `{**a, **b}` | 새 Map에 `a.putAll`, `b.putAll` | `judge.py` 결과 합치기 |
| `next((x for x in xs if 조건), [])` | `xs.stream().filter(조건).findFirst().orElse(List.of())` | `judge.py` 출처 찾기 |
| `if __name__ == "__main__":` | `public static void main` | `scripts/*.py` |
| `None` | `null` | |
| 들여쓰기 | `{ }` 중괄호 | 파이썬은 들여쓰기가 문법 |

### 파일을 읽는 순서 추천
1. **`ramen_bot/judge.py`의 `identify()`** — 전체 흐름의 입구 (보기 → 판단)
2. **`ramen_bot/vision.py`의 `extract_features()`** — VLM에 무엇을 묻는지 (`PROMPT`, `SCHEMA`)
3. **`ramen_bot/judge.py`의 `judge()`** — 검색 → 후보 → LLM 판단
4. **`ramen_bot/knowledge.py`의 `load_chunks()`, `search()`** — 문서를 자르고 검색하는 방법
5. **`ramen_bot/answer.py`의 `explain()`** — 화면용 설명 조립
6. **`ramen_bot/api.py`** — Spring 컨트롤러처럼 읽으면 된다

각 함수에 한국어 주석으로 "왜 이렇게 했는지"를 적어 두었습니다.

## 작은 수정 연습 문제

코드를 직접 조금씩 바꿔 보면서 이해를 확인하는 연습입니다. 바꾼 뒤에는 `git diff`로 변경을 확인하고, 되돌리려면 `git checkout -- 파일이름`을 쓰면 됩니다.

| 난이도 | 연습 | 힌트 |
|---|---|---|
| ⭐ | 검색 후보 수를 5 → 3으로 줄이고 `eval_rag.py`를 돌려 정답률·검색 재현율 변화 보기 | `judge.py`의 `judge(features, k=5)` |
| ⭐ | 데모 화면의 제목 문구 바꾸기 | `web/index.html`의 `<h1>` |
| ⭐⭐ | 토핑 체크리스트에 "반숙 달걀"을 추가하기 | `vision.py`의 `TOPPINGS`와 `judge.py`의 `TOPPING_KO`에 한 줄씩 |
| ⭐⭐ | 이미지 축소 크기를 1024 → 768로 바꾸고 속도·정확도 비교 | `vision.py`의 `MAX_SIDE` |
| ⭐⭐⭐ | 새 라멘 종류(예: 츠케멘) 지식 문서를 추가하고 인덱스 다시 만들기 | 기존 `knowledge/*.md` 형식을 복사 → `python scripts/build_index.py` |
