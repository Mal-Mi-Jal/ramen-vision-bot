## Before 3. 사진 인식 (`scripts/test_vision.py`) — 2026-09-25

**사진:** `samples/ramen.jpg`, 현재 `samples/aburasoba_1.jpg` (4000x3000 → 1024x768로 축소해서 전송). 국물 없는 마제소바/아부라소바 계열. 토핑: 적양파, 차슈(슬라이스+깍둑썰기), 멘마, 김, 튀긴 양파, 시라가네기, 고춧가루.

**모델 답변:**
> 1. 이에케
> 2. 양파, 돼지고기, 노란색 토핑, 나물, 김
> 3. 국물 색이 흰색이고 면이 굵기 때문에 이에케라멘이라고 판단됩니다.

**소요 시간:** 7.1초

**채점:**
- 종류 ❌ — 이에케 아님 (국물·시금치 없음)
- 근거 ❌ — **존재하지 않는 "흰 국물"을 봤다고 함** (할루시네이션)
- 토핑 △ — 양파·돼지고기·김은 맞음. 멘마·튀긴 양파 등은 뭉뚱그리거나 놓침

**교훈:** VLM은 "보이는 물체"는 어느 정도 잡지만, 그걸 라멘 종류로 연결하는 "판단"(도메인 지식)이 약하다. Before 2에서는 이에케를 "가는 면"이라더니 여기서는 "굵은 면이라 이에케"라고 해서 지식 자체도 일관성이 없다.
→ 설계 방향: **VLM은 시각 특징 추출만, 종류 판단은 RAG(라멘 지식 문서)로 분리.**

## Before 4. 기준 정확도 (baseline) — 2026-09-25

`scripts/eval_baseline.py`: 사진 23장, 9종류. 정답은 파일 이름(`shio_1.jpg` → shio). 모델에게는 **종류 이름 목록만** 주고(특징 설명 없음), Structured Output(JSON 스키마, label은 enum)으로 답하게 함. `temperature=0`.

| 종류 | 사진 수 | A. label 먼저 | B. 근거 먼저 (`--reason-first`) |
|---|---|---|---|
| shio | 7 | 1 | 0 |
| shoyu | 4 | **3** | 0 |
| aburasoba | 3 | 0 | 0 |
| ieke / shoyupaitan / toripaitan | 각 2 | 0 | 0 |
| donkotsu / miso / karai | 각 1 | 0 | miso 1 |
| **전체** | **23** | **4/23 = 17%** | **1/23 = 4%** (16장이 JSON 깨짐) |
| 평균 시간 | | 3.2초 | 9.1초 |

비교 기준: 9종류 무작위 찍기 ≈ 11%, "전부 shio"라고 답하기 = 7/23 ≈ 30%. **→ 7B VLM 단독은 찍기 수준.**

결과 파일: `results/baseline_label_first_*.json`, `results/baseline_reason_first_*.json`

### 관찰
1. **한 답으로 쏠림:** A에서 23장 중 12장을 `ieke`로 답함. 모르면 특정 라벨로 도망가는 편향.
2. **라벨과 근거가 모순됨:** A는 스키마상 label을 먼저 생성하고 reason을 나중에 씀 → 결론을 먼저 정하고 근거를 짜맞춤. 예: label=`ieke`인데 reason은 "돈코츠 라멘의 특징"이라고 씀.
3. **"근거 먼저"(B)는 오히려 망가짐:** 이론상 관찰→근거→결론 순서가 더 나아야 하지만, 7B 모델은 한국어 reason을 끝없이 늘어놓거나 토핑을 반복("파인애플, 파인애플, ..." / "파스타, 파스타, ...")하다 출력 상한(512토큰)에 걸려 JSON이 잘림. 모델이 작고 한국어에 약한 탓.
4. **시각 특징 추출도 불안정:**
   - 면 굵기: 23장 **전부 "가는 면"** → 쓸모없는 특징 (이에케·아부라소바는 굵은 면)
   - 국물 유무: 아부라소바 3장 중 1장만 "국물 없음"으로 맞힘
   - 국물 색: 쇼유 4/4 "진한 갈색", 토리파이탄 2/2 "뽀얀 흰색"은 그럴듯함. 시오는 투명/갈색/흰색으로 제각각
   - 토핑: 육회, 오징어, 파스타, 파인애플 등 **없는 재료를 지어냄**

### 다음 개선 아이디어
- VLM에게는 **짧은 선택형 특징만** 묻기(국물 유무, 국물 색 5지선다, 면 굵기 3지선다) → 한국어 자유 서술 줄이기
- 내부 추론은 영어로, 사용자 답변만 한국어로
- 판단은 RAG(종류별 특징 문서)로 넘기기
- 더 큰/새로운 VLM 비교 (8GB VRAM 안에서)

## 실험 5. VLM에게 "보기"만 시키기 (특징 추출) — 2026-09-25

`scripts/eval_features.py`: 라멘 종류는 묻지 않고 눈에 보이는 특징 4개만 **영어 선택형(enum)** 으로 질문. 자유 서술 없음. 각 선택지는 "어떻게 보이는지"만 정의(라멘 지식은 안 줌). 정답은 사진을 보고 직접 붙인 `data/labels.csv`.

| 특징 | 정확도 | Before 4(자유 서술)와 비교 |
|---|---|---|
| soup (국물 유무) | **23/23 = 100%** | 아부라소바 1/3 → 3/3 |
| clarity (투명/탁함) | 17/23 = 74% | — |
| color (국물 색) | 18/23 = 78% | — |
| noodle (면 굵기) | 7/15 = 47% | 전부 "가는 면" → 여전히 불안정 |
| 평균 시간 | **1.2초** | 3.2초 (출력이 짧아서) |

결과 파일: `results/features_*.json`

### 관찰
1. **질문 방식만 바꿔도 크게 좋아짐:** 같은 7B 모델인데 "종류 맞히기 + 한국어 서술" → "보이는 것만 영어 선택형"으로 바꾸자 국물 유무 100%. 반복 루프·JSON 깨짐 0건.
2. **틀리는 패턴이 일정함 (고칠 수 있는 오류):**
   - 쇼유 4장 전부 clarity=cloudy → **진하게 어두운 국물을 "탁하다"로 착각.** 색(dark_brown)은 4/4 정답이라, 쇼유 판별에는 색만으로 충분.
   - karai(붉은 국물)를 light_brown으로 봄. toripaitan_2를 pale_gold로 봄.
3. **면 굵기는 믿을 수 없음 (47%):** 1024px 축소 사진에선 면 굵기 구분이 어려움. 판단 근거로 쓰지 않거나 가중치를 낮춰야 함.
4. **라벨 확인 필요:** shio_2(약간 탁한 노란 국물), shio_4(호박색 국물), shoyupaitan_2(금색에 가까움)는 정답 라벨 자체가 애매.

### 다음 단계에 주는 의미
- 특징만으로도 종류가 상당 부분 갈림: 국물 없음 → 아부라소바 / 투명+옅은 금색 → 시오 / 진한 갈색 → 쇼유 / 뽀얀 흰색 → 토리파이탄 / 붉은색 → 카라이.
- 연갈색+탁함 그룹(돈코츠·이에케·미소·쇼유파이탄)은 **색만으로 구분 불가** → 토핑(이에케=시금치+김 3장, 미소=옥수수 등)과 RAG 지식이 필요한 지점.

## 실험 6. RAG 연결 (After) — 2026-09-25

파이프라인 (`ramen_bot/`, `scripts/eval_rag.py`):
```
사진 → [vision] 특징 + 토핑 체크리스트(예/아니오) → 한국어 검색어
     → [knowledge] Chroma + bge-m3 검색 → 후보 종류
     → [judge] 특징 + 후보 문서로 LLM(qwen2.5vl 텍스트 모드) 판단 → 종류 + 출처(코드가 붙임)
```

| 버전 | 바꾼 점 | 정답률 | 검색 재현율 |
|---|---|---|---|
| Before (실험 4) | VLM 단독 | 4/23 = 17% | — |
| v1 | 전체 섹션에서 top-6 검색, 9종류 중 선택 | 5/23 = 22% | 17/23 = 74% |
| v2 | "사진으로 구분하는 법" 섹션만 검색(top-4), 후보 중에서만 선택, 문서에 `style=키` 표시, 오탐 토핑 2개 제거 | 12/23 = 52% | 14/23 = 61% |
| **v3** | **하이브리드 검색** (국물 유무는 메타데이터 필터), 판별 섹션에서 비교 문장 분리, top-5 | **13/23 = 57%** | **21/23 = 91%** |

종류별 (v3): aburasoba 3/3, ieke 2/2, miso 1/1, shio 5/7, shoyu 2/4, donkotsu 0/1, karai 0/1, shoyupaitan 0/2, toripaitan 0/2.
결과 파일: `results/rag_v1_*.json`, `results/rag_v2_*.json`, `results/rag_v3_*.json`

### 버전별로 배운 것
- **v1 → 20/23을 "shoyu"로 답함.** 원인 두 가지:
  1. 검색: 모든 문서에 "국물" 섹션이 있어서 그 섹션들과 basics 문서가 상위를 독차지 → 종류를 가르는 핵심 섹션이 밀려남.
  2. 판단: 근거는 "투명 + 옅은 금색 → 청탕"으로 맞게 써 놓고 결론은 shoyu. 한국어 문서 제목("시오 라멘")과 영문 답(`shio`)을 연결하다 헷갈림.
- **v2 → 판단은 좋아졌지만 검색이 문제.**
  - **임베딩은 부정("국물 없음")에 약하다**: "국물 없음" 검색어가 국물 있는 문서들과 더 가깝게 나와 아부라소바 3장을 전부 놓침.
  - **허브 문서**: 토리파이탄 판별 섹션에 "돈코츠와 구분", "쇼유파이탄과 구분" 같은 비교 문장이 많아 온갖 검색어와 가까워짐(검색 실패 9건 중 6건에서 1위).
  - VLM 재실행 없이 검색 방식만 바꿔 재현율을 비교: 벡터만 14/23 → 국물 필터 추가 18/23 (k=4), 20/23 (k=5).
- **v3 → 검색 재현율 91%.** 이제 오답의 대부분이 검색이 아니라 **보기(VLM)와 판단(LLM) 단계**에서 생김.

### v3 남은 오답 10개 분석
| 원인 | 건수 | 예 |
|---|---|---|
| VLM이 잘못 봄 | 5 | 쇼유를 cloudy로(2), karai 붉은 국물을 light_brown으로, toripaitan_1에 없는 베니쇼가를 봄, shio_4 호박색 |
| 판단 LLM 실수 | 3 | 이에케는 "시금치 **+** 김" 조합인데 **김만 보고** ieke로 판단 (karai_1, shoyupaitan_1·2) |
| 원래 애매함 | 2 | shio_2(삼계탕 같은 국물), toripaitan_2(색 경계) |

### 한계 (정직하게)
- **같은 23장으로 평가하면서 v1→v3를 고쳤다.** 즉 테스트 세트에 맞춰 튜닝한 셈이라 57%는 낙관적인 수치일 수 있다. 문서 수정은 "검색어와 같은 어휘로 쓰기", "비교 문장 분리"처럼 일반적인 변경만 했고, 테스트 사진에서 얻은 "프로젝트 관찰" 섹션은 검색에서 뺐다(정답 누수 방지). 그래도 **새 사진(held-out set)으로 다시 재야** 진짜 성능을 말할 수 있다.
- 사진 23장, 종류별 1~7장이라 종류별 정답률은 통계적으로 의미가 약하다.

쇼유파이탄은 메이저한 종류가 아니라서 범위에서 뺐다 (사용자 결정). `knowledge/shoyupaitan.md` 삭제, 다른 문서의 "쇼유파이탄과 구분" 문장 정리. 사진 2장은 그대로 두고 `eval_rag.py`가 지식 문서 없는 종류를 자동으로 건너뛴다.

## 실험 8. 새 사진(held-out)으로 검증 — 2026-09-25

튜닝에 쓰지 않은 **위키미디어 공용 사진 25장**(8종류)으로 코드 수정 없이 채점. 30장 후보 중 5장 제외(가게 외관 3장, 라벨이 의심스러운 2장). 출처·저작자·라이선스는 `data/test_sources.csv`, 사진은 `samples_test/`(gitignore).

| | 튜닝에 쓴 사진 (samples/, 21장) | **새 사진 (samples_test/, 25장)** |
|---|---|---|
| Before: VLM 단독 (`eval_baseline.py`, 8종류) | — | **7/25 = 28%** |
| After: RAG v3 (`eval_rag.py`) | 16/21 = 76% | **15/25 = 60%** |
| 검색 재현율 | 90% | 88% |

→ **새 사진에서도 VLM 단독 대비 2배 이상(28% → 60%).** 튜닝 사진(76%)보다 16%p 낮아서, 앞선 수치가 과적합으로 부풀려져 있었음을 확인.

종류별 (After): shio 3/3, karai 2/2, aburasoba 3/4, shoyu 3/4, ieke 2/4, miso 2/4, donkotsu 0/1, **toripaitan 0/3**.
결과 파일: `results/rag_samples_test_*.json`, `results/baseline_label_first_samples_test_*.json`

### 새로 드러난 약점 (고치지 않고 기록만 — 고치면 이 세트도 튜닝용이 되어버림)
1. **"탁한데 노란빛" 국물을 시오로 판단 (4건):** 실제 토리파이탄은 노란빛 크림색인 경우가 많은데, VLM이 `pale_gold`로 보고 판단 LLM은 투명도(`cloudy`)를 무시한 채 색만 보고 shio를 고름. 지식 문서도 토리파이탄을 "새하얀 크림색"으로만 설명해서 노란빛 토리파이탄을 못 잡음 → **문서 보강 + 투명도 규칙**이 다음 개선 후보.
2. 이에케 2장도 노란빛 탁한 국물 → toripaitan으로 오판.
3. aburasoba_1: 파가 수북해 VLM이 국물 있음(soup=yes)으로 오인식. 국물 유무 100%는 우리 사진 기준이었고 새 사진에선 3/4.
4. 위키미디어 사진은 대부분 일본·해외 가게 사진이라 사용자가 찍은 사진과 분포가 다르다. 사용자가 앞으로 찍는 사진을 별도 테스트 세트로 모으면 가장 현실적인 평가가 된다.

### 다음 개선을 할 때의 원칙
개선은 **samples/(튜닝용)** 기준으로 하고, samples_test/는 최종 확인에만 쓴다. samples_test로 다시 튜닝하게 되면 새 held-out 사진이 또 필요하다.

## 실험 9. 설정값 바꿔 보기 (연습 문제) — 2026-09-28

`docs/tech-notes.md`의 연습 문제로 세 가지를 바꿔 보고, 효과를 따로 알 수 있게 조합별로 `samples/`(튜닝용 21장)에서 측정. VLM 특징은 이미지 크기별로 한 번만 뽑고 판단 단계만 k를 바꿔 재사용.

| 실행 | 반숙 달걀 체크 | 이미지 긴 변 | 후보 수 k | 정답률 | 검색 재현율 | VLM 시간/장 |
|---|---|---|---|---|---|---|
| 기준 (실험 7) | ✗ | 1024 | 5 | 16/21 | 19/21 | — |
| A | ✓ | 1024 | 5 | 15/21 | 18/21 | 4.05초 |
| B | ✓ | 1024 | **3** | 14/21 | **16/21** | 4.05초 |
| C | ✓ | **768** | 5 | 16/21 | 19/21 | **3.55초** |
| D | ✓ | 768 | 3 | 14/21 | 16/21 | 3.55초 |

결과 파일: `results/practice_ablation_samples_*.json`

### 해석
1. **k=3은 확실히 나쁘다.** 1024px(A→B), 768px(C→D) 모두에서 검색 재현율이 2장씩 떨어짐. 조건을 바꿔도 같은 방향으로 반복되는 결과라 신뢰할 수 있다. k=5 유지.
2. **반숙 달걀: 인식은 정확하지만 판별에는 쓸모없다 (특징 선택).** VLM이 "있다"고 본 10장은 사진 확인 결과 거의 모두 실제로 달걀이 있었다. 하지만 반숙 달걀은 거의 모든 라멘에 올라가는 토핑이라 종류를 가르는 단서가 아니고, 어떤 지식 문서도 판별 기준으로 쓰지 않는다. 검색어에 소음만 더해 1장을 더 틀림(shio_2). → **"잘 보이는 특징"과 "구분에 쓸모 있는 특징"은 다르다.**
3. **768px: 12% 빠르고 정확도는 비슷.** 다만 21장에서 1장 차이는 우연 범위라 "더 좋다"고 결론 내릴 근거는 부족하다. held-out 60%도 1024 기준이라 바꾸면 재측정이 필요하다.

### 결정
세 변경 모두 되돌림 (k=5, 1024px, 반숙 달걀 제거). 다음에 속도가 중요해지면 768px은 held-out 세트로 다시 검증할 후보.

## 실험 10. 라멘이 아닌 사진 거절하기 (관문 추가) — 2026-10-12

**발견**: 라멘이 아닌 사진(전통 장신구)을 올리자 "아부라소바"로 판별됨. VLM은 "국물 없음"이라고 정확히 답했고, 국물 필터로 후보가 아부라소바 하나만 남아 LLM 확인까지 생략됐다. 8종류 중 하나를 반드시 고르는 **닫힌 집합(closed-set) 분류**라서 "해당 없음"을 처리하지 못한 설계 빈틈. 특징 추출 프롬프트도 첫 문장이 "Look at the ramen bowl in this photo"로 라멘을 전제하고 있었다.

**해결**: 특징 추출 전에 **관문(gate)** 을 둠 — `vision.is_noodle_dish()`가 "면 요리 그릇 / 다른 음식 / 음식 아님" 중 하나를 고르게 하고, 그릇이 아니면 `judge.identify()`가 검색·판단 없이 `not_ramen`을 반환. 화면은 오류 대신 안내 문구를 보여 줌.

| 시도 | 라멘 아닌 사진 5장 거절 | 튜닝용 라멘 사진 | 문제 |
|---|---|---|---|
| A. 특징 추출 프롬프트에 `is_ramen` 질문 추가 + 첫 문장 수정 | 5/5 | 15/21 (−1) | 마제소바(aburasoba_1)를 "라멘 아님"으로 거절, **기존 특징까지 흔들림**(toripaitan_2 국물 있음→없음). 한 번에 두 가지를 바꾼 탓 |

| **C. 별도 호출, 3지선다 + "애매하면 그릇"** | **5/5** | **16/21 (변화 없음)** | — |

C 최종 확인:
- 튜닝용 21장(+쇼유파이탄 2장): 거절 0장. 사진별 예측·검색 결과가 실험 7과 **완전히 같음** (관문이 기존 특징 추출에 영향 없음)
- 테스트용 26장(실험 8의 25장 + 사용자가 추가한 ieke_5): 거절 0장, 16/26 = 62%, 검색 재현율 24/26. 실험 8과 다른 사진은 toripaitan_2 하나(시오 → 이에케, 둘 다 오답) — 아래 환경 변화 때문이며 관문과 무관
- 웹 화면: 라멘이 아닌 그림을 업로드 → "🤔 라멘 사진이 아닌 것 같아요…" 안내, 결과 카드 숨김
- 비용: 관문 호출이 사진당 약 1초 추가

결과 파일: 시도 A `results/rag_samples_v10a_*.json`, 시도 B `results/rag_samples_v10b_*.json`, 최종 C `results/rag_samples_20261012_1515.json` · `results/rag_samples_test_20261012_1522.json`

### 한계 (정직하게)
- 라멘이 아닌 사진은 **5장뿐**이고(장신구 1 + Windows 기본 배경화면 4), 관문 문구를 고칠 때 이 5장을 계속 봤기 때문에 독립된 검증 세트가 아니다. 음식 사진(파스타·우동 등 다른 면 요리는 의도적으로 통과시킴)을 포함한 별도 세트로 다시 재야 한다.

## 트러블슈팅 기록

### Structured Output JSON이 중간에 잘림 (2026-09-25)
```
json.decoder.JSONDecodeError: Unterminated string ...
```
- 원인: 모델이 같은 말을 반복하는 루프에 빠져 출력이 끝나지 않음.
- 해결: `num_predict: 512`(출력 토큰 상한), `toppings`에 `maxItems: 10`, JSON 파싱 실패 시 `invalid`로 기록하고 다음 사진으로 진행.

### 이미지가 컨텍스트 한도를 초과 (2026-09-25)
```
request (4129 tokens) exceeds the available context size (4096 tokens)
```
- 원인: 4000x3000 원본 사진을 그대로 보냄. Qwen2.5-VL은 약 28x28px당 1토큰이라 큰 사진은 토큰이 많고, Ollama 기본 컨텍스트는 4096.
- 해결: Pillow로 긴 변 1024px로 축소(약 1000토큰) + `options={"num_ctx": 8192}`.
